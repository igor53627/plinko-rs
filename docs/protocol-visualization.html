Plinko PIR, one ball at a time

An interactive companion to the Plinko paper (ePrint 2024/318) and to plinko-rs. Each figure runs the algorithm that its text describes, with small sizes and a toy hash in place of AES. The figures give no security.

The sampler alone keeps the order of the balls

Plinko is a private information retrieval scheme: a client reads a record of a database, and the server does not learn which one. The client prepares hints before it sends a query. The tool that makes the hints fast to find is a sampler that throws n balls into m bins. The paper calls it a pseudorandom multinomial sampler (PMNS).

Move the slider: ball 0 is always in the first bin that has a ball, and a higher ball never lands to the left of a lower one. The sampler needs only the nodes on one path of the tree, so one ball costs O(log m) nodes.

def trace_ball(k, x, n, m):
    low, high, count = 0, m - 1, n
    while low < high:
        mid = (low + high) // 2
        left = binomial(count, 1/2, PRF(k, (low, high)))
        if x < left:  # the ball goes left
            high, count = mid, left
        else:
            x, low, count = x - left, mid + 1, count - left
    return low

The paper has a probability p at each node. plinko-rs needs m to be a power of two, so p is always 1/2, and the number of balls for the left child is the number of set bits among count keystream bits.

A permutation hides the order

A function that keeps the order of its inputs is not pseudorandom. Plinko sends the input through a keyed permutation first. The permutation is a Swap-or-Not shuffle (Hoang, Morris and Rogaway, 2012). Each round pairs x with a partner and flips one keyed coin for the pair: swap, or not.

def swap_or_not_round(k, x, round, N):
    partner = (round_key(k, round) - x) mod N
    if PRF(k, round, max(x, partner)) == 1:
        return partner  # swap
    return x

The two values of a pair see the same coin. A round is thus its own inverse, and the inverse permutation runs the same rounds in the opposite order.

Together they make a function that runs backward

The invertible PRF (iPRF) of the paper is the permutation, then the sampler.

F(k, x) = S(kpmns, P(kprp, x))

To invert an output y, read the balls of bin y from the tree and send each ball back through P-1. The cost grows with the number of results, not with the number of inputs.

In the protocol, an input is the number of a hint and an output is an offset in a block. Each block has its own key. The figure shows the function of block 0.

A hint is one record from each block of a subset

The database is cut into c blocks of w records. Hint j has a random subset of the blocks. In each block k of its subset it holds one record: the record at offset F(K[k], j). The hint stores only the XOR of these records, its parity.

The client makes the hints in one pass over the database (HintInit, Fig. 7 of the paper). For each record it runs one iPRF inverse. The result is the list of hints that read this offset in this block.

for i in 0..n:  # one pass over the database
    d = D[i]
    (block, offset) = (i // w, i mod w)
    for j in F_inverse(K[block], offset):
        if j < lambda*w:  # regular hint: c/2 + 1 blocks
            if block in H[j].subset:
                H[j].parity ^= d
        else:  # backup hint: c/2 blocks, two parities
            if block in T[j].subset:
                T[j].parity_in ^= d
            else:
                T[j].parity_out ^= d

A backup hint keeps a parity for its subset and a parity for the other blocks. A query later turns one backup hint into a regular hint.

A query spends one hint, and an update repairs a few

To read record i in block b, the client needs a hint that holds i. One iPRF inverse gives the candidates. The client takes block b out of the subset of the hint and sends the other blocks with their offsets, next to a second subset of the same size. The server returns one parity for each subset. The parity of the hint and the parity from the server differ by exactly record i.

A hint that was sent is not used again: a second use would show the server what the two queries have in common. A backup hint takes its place, with record i as its extra record.

When a record changes, the client gets the index and the XOR of the old and the new value. One iPRF inverse gives the hints that hold the record, and the client corrects their parities. It reads no other hint.

plinko-rs is a library for a database of fixed-size records. Each client downloads the database and runs HintInit. The full Ethereum state is not a target: at that size the download is 73.4 GB and HintInit needs about 300 core-hours (extrapolated).
